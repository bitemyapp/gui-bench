# gui-bench

`gui-bench` is a native, apples-to-apples benchmark harness for zgui, GPUI-CE and aizome-kit. It runs the same deterministic UI model through small and large updates, records every frame and resource sample into one versioned JSON document, and produces a standalone interactive ECharts report.

The source trees at `../zgui`, `../gpui-ce` and `../sekka` are never modified. zgui is a local path dependency, and so is aizome-kit, from Sekka's checkout at `../sekka/desktop/aizome`. GPUI-CE is copied to `vendor/gpui-ce` (without `.git` or `target`) because the diagnostic build adds timing probes inside its layout and WGPU pipelines. The vendored copy represents the upstream working tree, including any pre-existing local changes.

## Quick start

Run this from the repository on a quiet desktop session with the benchmark windows unobscured:

```sh
cargo run -p gui-bench -- preflight
cargo run -p gui-bench -- run --preset smoke --diagnostic --repetitions 1
```

The second command builds the adapters with the `bench-run` profile, runs headline and diagnostic passes, checkpoints raw data to `results/latest.json`, and writes `results/latest.html`. The HTML is completely offline: ECharts, the data, CSS, and report logic are embedded in it.

On NixOS, `nix develop` gives the pinned toolchain and the libraries the three frameworks link and open at run time.

The adapters are intentionally built in separate Cargo invocations, and only those a run asks for with `--framework`. Their upstream dependency graphs enable an incompatible combination of third-party derive features when Cargo unifies the graphs in one invocation; the benchmark executables are separate processes, so isolation also matches how they run.

Other useful commands:

```sh
cargo run -p gui-bench -- list --preset standard
cargo run -p gui-bench -- run --preset standard --repetitions 3
cargo run -p gui-bench -- run --preset full --framework zgui --scenario resize
cargo run -p gui-bench -- report results/latest.json
cargo run -p gui-bench -- summary results/latest.json
cargo run -p gui-bench -- run --preset rows --framework aizome-kit --diagnostic
```

Use at least three repetitions for comparisons. `smoke` is a correctness check, `standard` is the normal characterization matrix, and `full` is intended for a dedicated, idle machine. `rows` changes one node of a column of 1,000, 3,000 and 10,000 live rows a tick (its label, its fill, its size): the update that costs what the unchanged rows cost. `summary` prints a run as Markdown tables, every scenario and framework at once. Do not compare dev-profile adapter binaries; the runner deliberately builds adapters with optimized, thin-LTO `bench-run` settings.

## What is compared

Every condition is generated by `bench-core`, so every adapter receives an identical serialized scenario, deterministic node numbering, window size, update selection, warmup, and sample count. zgui and GPUI-CE draw the bundled IBM Plex Sans; aizome-kit's text element draws in the theme's families only, so its labels are in Archivo, the kit's interface face, at zgui's 12 px.

The matrix separates:

- cold first frame and idle frame-loop overhead;
- paint-only, layout-affecting, text, and keyed structural changes;
- sparse, medium, and full-document updates;
- flat, wide, balanced, and deep layout topology;
- minimal and decorated styles (background, border, radius, and shadow);
- mutation-to-observed-frame latency under a complex tree;
- alternating step resizes and continuously changing resize storms.

“Stimulus latency” starts immediately before the benchmark mutation or resize request and ends at the framework’s post-frame callback. It is an application scheduling/update-to-frame measure, not physical mouse-to-photon latency. OS input dispatch and display scanout require external hardware or compositor-specific tooling and are intentionally not presented as if they had been measured.

The adapters use each framework’s normal retained/immediate update semantics. They do not force both frameworks through an artificial common abstraction after the scenario is delivered; those differing invalidation and rebuild strategies are part of what the benchmark is meant to reveal.

aizome-kit is Elm's architecture on a CPU rasterizer: a message runs `update`, `view` describes the whole window again, and the kit lays that out, compares it with the last tree and redraws the rectangles that differ. Three things follow for its adapter.

- **The model is zgui's.** Each node keeps the tick that last affected it and shows its changed state while that tick is odd. GPUI's adapter can leave a node changed for many ticks running, because GPUI rebuilds and redraws everything regardless; a toolkit that draws what differs would have nothing to draw.
- **A frame is a display pass.** The kit draws a window only once its last frame has shown, so the start of a pass is its frame tick, the point GPUI's `on_next_frame` marks. The window's root is a widget of the adapter's that sends the program a message each time the window draws; the program answers with the next mutation. Stimulus latency runs from the mutation to the start of the pass that draws it. The frame before that one is still being rasterized on the render thread meanwhile, so the kit's program-thread and render-thread stages overlap from one mutation to the next where the other two frameworks' run end to end.
- **Every build draws.** The root invalidates one point of itself at each build, so a mutation whose nodes are all out of sight is still followed by a pass (of that one point) and the run goes on. For the passive and resize workloads it invalidates the whole window instead: the redraw GPUI's animation frame and zgui's `request_redraw` ask for. A kit window that nothing changes draws no frames at all.
- **Content keeps its height past the window.** The tree sits in a widget of the adapter's that lays it out as tall as it comes, as CSS's `overflow: hidden` leaves a column in the other two. A kit column gives a child that doesn't fit the room that is left, which past the window's bottom is none: without that widget the items out of sight had no height, and a decorated one still drew its shadow there. The results of 2026-11-09 before 20:00 were made without it; see `results/runnymede-2026-11-09-kit.md`.

Decorated items draw their rounded corners and soft shadow with the canvas under the kit, in a widget of the adapter's: the kit's own container is square, and its shadow hard.

## Measurements

Headline passes retain only the probes needed to identify frames and latency. Diagnostic passes are separate because detailed instrumentation has a cost.

Raw frame records include frame interval, stimulus latency, sample phase, observed window size, validity, and framework-internal memory. Diagnostic records additionally include nullable pipeline stages:

| Report field | zgui | GPUI-CE vendor | aizome-kit |
|---|---|---|---|
| view build | reactive flush | adapter `Render` element-tree construction | the program's `view` |
| style | cascade/restyle | folded into GPUI element/layout registration; reported unavailable | none: elements carry their look |
| layout | zgui layout phase | Taffy layout computation | layout of what `view` returned |
| prepaint | box/pre-layout work | GPUI prepaint excluding measured layout computation | the rest of the kit's build: mounting the elements, placing and hashing every node, the comparison with the last tree |
| paint | display-list emission | GPUI scene paint traversal | drawing recorded on the program's thread |
| rasterize | on the GPU | on the GPU | the damaged rectangles rasterized on the render thread |
| GPU prepare | buffer/vector/plan preparation | swapchain acquisition plus WGPU resource preparation | none |
| command encode | WGPU recording | WGPU command encoding | none |
| queue submit | acquisition-out through submit | `Queue::submit` CPU call | none |
| present | submit-out through present-out | swapchain `present` CPU call | the buffer brought up to date and committed |

These are CPU wall-clock durations around rendering-pipeline operations. They are not on-device GPU execution or desktop-compositor time; `device_gpu_timestamps` remains `false` unless a future adapter implements timestamp queries. Missing stages remain `null` instead of being fabricated as zero.

aizome-kit's stages come from three places. The adapter times its own `view` and, from its root widget, the layout of everything under it. The kit tells a program nothing when a build ends, but asks for its menus again as soon as one has: the build is timed from `view` returning to that call. Recording, rasterizing and presenting are Sidestep's own per-frame statistics (`sidestep_engine::stats`), read a frame late, once the render thread has finished with it.

The runner samples Linux process state every 50 ms:

- RSS, PSS, private clean+dirty memory, swap, and high-water RSS;
- user/system CPU ticks, context switches, thread count;
- per-process resident and shared GPU bytes from DRM `fdinfo`, with an NVML graphics-process fallback on NVIDIA;
- framework-owned GPU allocations where the framework has a memory report (zgui targets, scratch, atlases, buffers, and fixed allocation).

VRAM is reported as unavailable when neither the DRM driver nor NVML exposes a reliable per-process counter. This is preferable to substituting whole-device use, which would include the compositor and unrelated applications.

## Result format and data quality

`RunDocument` in `crates/bench-core` is the canonical schema. It carries a schema version, command line, host/display/GPU/Rust metadata, source revisions and dirty state, scenario definitions, repetitions, adapter capabilities, raw frames, raw resource samples, warnings, and completion status. The runner writes a temporary checkpoint and atomically replaces the requested JSON after every condition, so a long full run still leaves useful data if interrupted.

The report computes percentiles from raw measurement-phase samples. Warmup and invalid/coalesced frames stay in the JSON but are excluded from headline percentiles. Inspect warnings and the report’s data-quality panel before drawing conclusions, especially for occluded windows, unavailable VRAM, thermal drift, or a compositor that changes refresh behavior.

## Adding another framework

The framework boundary is the versioned JSON-lines protocol in `bench-core::AdapterEvent`, not a Rust UI trait. A new adapter should:

1. accept `--scenario <json>` and `--mode headline|diagnostic`;
2. print `hello`, wait for `start` on stdin, then print `ready`;
3. render the neutral `Scenario` using only the supported common feature subset;
4. emit raw `frame` events and a final `complete` event;
5. declare capabilities and leave unsupported measurements as `null`;
6. be added to the runner’s adapter executable registry and CLI values.

This keeps a future Dioxus Native adapter independent of both current framework APIs. Scenario generation, process/VRAM sampling, storage, statistics, and report rendering require no adapter-specific implementation.

## Updating the GPUI-CE vendor

Review the source working tree first, then run:

```sh
scripts/sync-gpui-ce.sh ~/Projects/gpui-ce
```

The script copies without `.git` and `target` and records the source revision/dirty state. Reapply or reconcile the small benchmark probes in `gpui/src/profiler.rs`, `gpui/src/window.rs`, and `gpui_wgpu/src/wgpu_renderer.rs` after an upstream update.

## This fork

Besides the aizome-kit adapter, this fork changes four things in the harness it came from:

- **zgui's adapter builds against zgui as it is now.** `Builder::for_surface` takes the window's handles where it took a surface; the adapter passes them. The JSON documents under `results/` are the harness author's, made with zgui at `586397bf`, its second commit.
- **zgui's structural update does something.** Every preset's structural scenario is wide, and only the flat topology's leaves read the `present` signals the update sets, so the scenario measured an update that changed nothing. Wide leaves read them now, as flat ones do.
- **The schema is at version 2.** `PipelineSample` has `rasterize_ns`, for a framework that rasterizes on the CPU, and `Framework` has `aizome_kit`. Version 1 documents load unchanged.
- **The runner has `summary`, the `rows` preset, and builds only the adapters a run uses.**

`results/runnymede-2026-11-09.md` is a run of all three frameworks on one desktop, with what went wrong in it.
